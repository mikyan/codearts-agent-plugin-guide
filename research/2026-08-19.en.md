[简体中文](2026-08-19.md)

This record extends the [2026-08-18 project-scope verification](2026-08-18.en.md). It tests whether Ponytail and Superpowers can be installed in the current user's CodeArts directory and used from projects with no project-scoped configuration.

CodeArts officially supports project `.codeartsdoer/skills` and user `~/.codeartsdoer/skills`, with project skills taking priority when names match. Plugins likewise support project and user directories. “User scope” means available to all CodeArts projects for the current user, not every user on the machine.

## Verification environment

- Windows 11 Build 26200
- CodeArts CLI 26.8.1
- PowerShell 7.6.5
- Node.js 24.14.1, npm 11.11.0, Git 2.53.0
- Custom model: `mimo/mimo-v2.5`
- Credentials were inherited only by CodeArts and were not printed or written to the repository
- Real calls used `codearts run --format json --sandbox`, without `--auto`

CodeArts desktop/IDE and Linux were not tested in this run.

## Problem discovered

Before testing, the user-root `%USERPROFILE%/.codeartsdoer/package.json` already contained CodeArts' bundled `@opencode-ai/plugin@26.8.1`. Merging third-party dependencies into this file caused both system npm and CodeArts automatic reification to try resolving that internal version from the public npm registry, which returned `ETARGET`.

User scope therefore cannot safely reuse the project dependency layout. The verified structure is:

```text
~/.codeartsdoer/
  plugins/<project>.ts
  vendor/<project>/
    package.json
    package-lock.json
    node_modules/
  skills/<copied-skill>/
```

Each project has an isolated `vendor` manifest. Its plugin loads the upstream entrypoint through a fixed path relative to `~/.codeartsdoer/plugins`, while skills are copied into CodeArts' native user directory. The user-root `package.json` remains unchanged.

## Rollback verification

The Ponytail and Superpowers user plugins, isolated `vendor` directories, and corresponding skill directories were completely moved out of the user CodeArts directory. Checks then confirmed that:

- neither third-party skill set remained discoverable;
- the SHA-256 of user-root `package.json` exactly matched its pre-test value;
- `codearts_cli.json`, credentials, and unrelated CodeArts plugins were unchanged.

Project installation had already been reproduced and rolled back in two isolated projects. The formal guides now document installation and removal for both scopes.

### Reused verification method

This run actively followed the repository's [CodeArts plugin compatibility skill](../skills/codearts-plugin-compatibility/SKILL.md):

1. Inspect the pinned `SKILL.md`, local resources, license, and executable scripts.
2. Copy only the selected skill into an isolated project's `.codeartsdoer/skills/<skill-name>` without running upstream installers or installing unrelated dependencies.
3. Check its name and resolved path with `codearts debug skill`, then require an explicit skill call in a real `codearts run --format json --sandbox --model mimo/mimo-v2.5` session.
4. Reproduce the final process from zero in a second isolated project.
5. Install the same skills under `~/.codeartsdoer/skills/<skill-name>` and call them again from an independent directory with no project override.
6. Remove only the test targets, confirm neither scope discovers the skills, and confirm the user-root `package.json` hash is unchanged.

All ten candidates completed discovery, a successful `skill` event, and an attributable result. The OpenAI case also completed one relative-path `read` inside the skill. No AK, SK, or model API key was written to command output or the repository. The custom-provider sessions used non-secret AK/SK placeholders; the actual model credential remained in the local Provider configuration in `codearts_cli.json`.

### Compatibility patterns and exceptions

- The representative capabilities are content-oriented skills. Native CodeArts skill placement was sufficient; no OpenCode plugin or npm wrapper was needed first.
- Upstream source may live under `skills/.curated/...`, `skills/cloud/...`, or `pm-execution/skills/...`; CodeArts installation still uses `.codeartsdoer/skills/<skill-name>`. Upstream parent directories must not be copied into the native target structure.
- CodeArts CLI 26.8.1 uses YAML frontmatter for discovery but omits it from content returned by the `skill` tool. An initial Humanizer smoke test that asked about a frontmatter field was therefore invalid; a body-based capability assertion passed. Future assertions should come from the skill body.
- Humanizer's `skills/humanizer/SKILL.md` is a Git symlink to the repository-root `SKILL.md`. A default Windows checkout materializes it as a plain file containing only `../../SKILL.md`, so the guide copies the pinned root file and records `Adapter Required`.
- Scientific Experimental Design's Python scripts passed static review and syntax compilation, but `numpy`, `pandas`, and `pyDOE3` were not installed and CodeArts did not execute the scripts. The result is therefore `Partial`.
- Basic Google GKE manifest generation passed, but no live cluster, `gcloud`, Google Developer Knowledge API, or inference workload was tested. The result is therefore `Partial`.
- Two format checks initially rejected correct content: the Conventional Commit was wrapped in a code fence and an Obsidian single-character response was wrapped in backticks. The checker was corrected after reviewing full tool events and actual text; no compatibility claim rests on the format false negatives.
- The first user rollback used an incorrect relative working directory. Path-boundary checks rejected every move and no file was removed; the exact rollback then passed using resolved absolute paths.

### Scope limits

The environment remained Windows 11, PowerShell 7.6.5, CodeArts CLI 26.8.1, and MiMo `mimo/mimo-v2.5`. CodeArts desktop/IDE, Linux, other models, and unselected skills in the ten repositories were not tested. `Works` means only that the selected skill needed no additional adapter within this boundary.
