## 发现的问题

测试前，用户根 `%USERPROFILE%/.codeartsdoer/package.json` 已包含 CodeArts 自带的 `@opencode-ai/plugin@26.8.1`。如果直接把第三方依赖合并进这个文件，再在用户根安装，系统 npm 和 CodeArts 自动 Reify 都会尝试从公共 npm Registry 解析该内部版本并返回 `ETARGET`。

因此个人级适配不能直接复用项目级依赖清单。验证通过的结构是：

```text
~/.codeartsdoer/
  plugins/<project>.ts
  vendor/<project>/
    package.json
    package-lock.json
    node_modules/
  skills/<copied-skill>/
```

每个项目拥有独立的 `vendor` 清单。插件使用相对于 `~/.codeartsdoer/plugins` 的固定路径加载上游入口，Skills 则复制到 CodeArts 原生个人级目录。用户根 `package.json` 保持不变。

### 复用的验证方法

本轮实际使用仓库内的 [CodeArts 插件兼容验证 Skill](../skills/codearts-plugin-compatibility/SKILL.md) 执行以下流程：

1. 审查固定 Commit 下的 `SKILL.md`、本地资源、许可证与可执行脚本。
2. 只把所选 Skill 复制到隔离项目的 `.codeartsdoer/skills/<skill-name>`，不执行上游安装脚本、不安装无关依赖。
3. 用 `codearts debug skill` 检查名称和来源路径，再用真实 `codearts run --format json --sandbox --model mimo/mimo-v2.5` 要求模型显式调用该 Skill。
4. 在第二个全新隔离项目从零复现同一流程。
5. 把同一组 Skills 安装到当前用户 `~/.codeartsdoer/skills/<skill-name>`，从没有项目级覆盖的独立目录再次调用。
6. 精确移除测试目标，确认项目级与个人级均不再发现这些 Skills，并确认用户根 `package.json` 哈希没有变化。

十个项目都完成了“发现 + 成功的 `skill` 工具事件 + 可归因结果”；OpenAI 的用例还完成了一次 Skill 内相对路径 `read`。测试过程中没有把 AK、SK 或模型 API Key 写入命令输出和仓库。自定义模型会话使用非秘密 AK/SK 占位值，真实模型凭据仍由本地 `codearts_cli.json` 中的 Provider 配置使用。

### 兼容规律与例外

- 这十个候选的代表性能力都是内容型 Skill。优先采用 CodeArts 原生 Skills 目录即可，无需先构造 OpenCode 插件或 npm 包装层。
- 上游源码可以位于 `skills/.curated/...`、`skills/cloud/...` 或 `pm-execution/skills/...` 等深层目录；安装到 CodeArts 时仍统一落到 `.codeartsdoer/skills/<skill-name>`。不要照抄上游父目录层级。
- CodeArts CLI 26.8.1 的 `skill` 工具返回正文但不返回 YAML Frontmatter。最初用 Frontmatter 字段做验收的 Humanizer 冒烟测试因此无效，改用正文能力后通过。后续验收应从 Skill 正文选择可观察断言。
- Humanizer 的 `skills/humanizer/SKILL.md` 是指向仓库根 `SKILL.md` 的 Git 符号链接。Windows 默认检出会把它变成只含 `../../SKILL.md` 的普通文件，因此指南复制固定 Commit 的仓库根文件，结论为 `Adapter Required`。
- Scientific Experimental Design 随附的 Python 脚本已完成静态审查和语法编译，但没有安装 `numpy`、`pandas`、`pyDOE3`，也没有让 CodeArts 执行脚本，因此只记为 `Partial`。
- Google GKE Skill 的基本清单生成通过，但未连接真实 GKE 集群、运行 `gcloud`、访问 Google Developer Knowledge API 或验证推理工作负载，因此只记为 `Partial`。
- 两次输出格式检查曾把正确结果误判为失败：Conventional Commit 被代码围栏包裹，Obsidian 单字符结果被反引号包裹。复核完整工具事件与实际文本后修正了测试器；兼容结论没有建立在格式误判上。
- 第一次个人级回滚使用了错误的相对工作目录，路径边界检查拒绝了全部移动，没有文件被误删；改用已解析的绝对路径后完成精确回滚。
