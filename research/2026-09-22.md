## 许可证与安全审查

- 10 个被安装的固定目录都只有一个 `SKILL.md`，没有 manifest、锁文件、 install/postinstall、二进制、下载器、遥测代码或运行时依赖。安装阶段只复制已读过并哈希的固定文件。
- 所有候选上游均声明 MIT；Agentic Awesome 自身代码为 MIT，聚合内容遵循其 `LICENSE-CONTENT` 和原始来源许可证。
- `devops-pipeline-builder`、`api-integration-architect` 和 `api-integration` 的正文包含部署、网络或密钥相关示例；本轮只做合成输入的只读设计，拒绝 Bash、文件、网络、浏览器和外部目录权限。
- `review-and-simplify-changes` 的完整流程可调用子 Agent 并修改代码；本轮明确使用小范围 `review-only`，没有启动子 Agent、读取 Git 或编辑文件。
- 第一次发布流脚本漏配 CodeArts 通道环境，6 次都在模型请求前返回 `Network request blocked`。这些基础设施失败没有 Skill 事件，已全部回滚；补齐与主验证相同的进程环境后，在新的隔离目录从零执行发布流，未把失败调用当作候选通过证据。

## 安装、发现、调用与回滚方法

主验证把每个固定候选复制到作用域专属 `vendor/agentic-awesome-<name>`，再复制到 CodeArts 原生 `skills/<name>`。每个作用域先运行真实 `codearts debug skill`，要求候选名与准确 `SKILL.md` 绝对路径唯一匹配；随后运行候选专用 `codearts run -m mimo/mimo-v2.5 --format json`，要求出现目标绝对路径的唯一 `skill:completed` 事件。

主验证 30/30 次安装、发现、加载和调用均通过技术断言。对两个最接近发布的候选又按拟发布流程执行：从 GitHub clone、对 `skills/<name>` 做 sparse checkout、checkout 固定 Commit、复制到原生目录，再完成相同调用。6/6 次发布流同样产生唯一目标 Skill 事件。

删除前逐次核对绝对目标必须位于对应 `.codeartsdoer` 根下；随后只删除准确 Skill 与 vendor 目录，再运行真实 `codearts debug skill`，要求原 `name + location` 匹配为零。
